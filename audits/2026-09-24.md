## Findings (sorted by severity)

### F-TRUST-1 — a comma kg on the live log is saved as 0; in History as null · bug · effort: hours · NEW
DEC-058 §1 (Emilio): *"'22,5' means 22.5. In weight fields the comma is a decimal point … The Swedish keypad may
only offer a comma."* That rule is implemented in only two places, `routine-item-parse.js:50` (routine editor Kg)
and `weight-step.js:18` (increment) [measured: `grep -rn "replace(','" src` → those 2 only]. The four places that
write a **logged set's** kg use plain `Number()`:

- `views/workout/item.jsx:223`, the live set log: `weight: isWeightedType(ex.type) ? Number(weight) || 0 : 0`
- `views/workout/item.jsx:585`, editing a set in the workout: `Number(weight)`
- `views/history/edit.jsx:189`, editing a History set: `Number(weight)`
- `views/history/add-set.js:59`, adding a History set: `Number(weight)`

The kg input is a text field with `inputMode="decimal"` (`ui/index.jsx:134-135`), so the phone's own decimal key
is what gets typed. Receipt [measured, node]:
```
live log Number("22,5")||0 = 0 | history edit Number("22,5") = NaN -> JSON {"weight":null}
```
So on the core loop, `22,5 kg` is stored as "no weight", with no error. That breaks DESIGN §1 ("the record is never
wrong"), and the next session's history prefill (`storage.js:517`) then shows a blank kg. The Tier 1 test list (#1)
only exercised the routine editor. [inferred] An iPhone set to a Swedish region shows `,` on the `decimal` keypad.
Whether any of Emilio's real sets are affected can't be seen from the code.

### F-TRUST-2 — warm-up and cardio sets record an effort ("Moderate") the user never saw · bug · effort: minutes–hours · NEW (existed at 2026-09-12, missed then)
`item.jsx:323` hides the Effort control for warm-up and cardio sets (`showEffort = currentType === 'work' && type
!== 'cardio'`). But `SetLogForm` keeps `effort` in state from `initialEffort` (`ui/index.jsx:413`, default 3 via
`initialSetFields`, `workout-log.js:536-539`) and submits it whether or not the control rendered
(`ui/index.jsx:433-438`). `completeSet` then stores `rpe: rpe ? Number(rpe) : null` (`item.jsx:227`), which is `3`.
Receipt [measured: `vite build` of `ui/index.jsx` + `react-test-renderer`, then submit]:
```
showEffort=false -> onComplete effort=3 (effort control rendered: false)
showEffort=true  -> onComplete effort=3 (effort control rendered: true)
```
History then prints it: `formatSetLine` (`ids.js:124`) adds `rpeLabel(3)`, so a warm-up reads
`WU set · 20 kg · 10 · Moderate`. It's invented data in the permanent record (DESIGN §1: *"can you name the record it
came from? If not, it must not appear as if the user entered it"*). Moderate is sanctioned only as the prefill of a
**visible** control. The test fixtures assume the opposite: `req-117.test.js:80`, `req-125.test.js:79` and
`skip-replace.test.js:117` all build warm-up sets with `rpe: null`, so no test catches it (see F-TEST-1).
Progression isn't affected: warm-ups are excluded (`model.js:376`) and cardio holds (`progress.js:131-142`).

### F-RISK-5 — in the "unreadable data" state, Import says it worked but nothing is saved · bug · effort: hours (plus a decision) · NEW
After a corrupt `workout-mvp-v9` load, `loadUnreadable` latches (`storage.js:199-201`) and `saveState` returns
`false` without touching the save-failed signal (`storage.js:208`). Import is the natural way to recover, but
`commitBackup` sets state (`exchange.js:293-296`) and Settings shows the "imported N workouts" banner regardless
(`Settings.jsx:71-75`). Nothing clears the latch (`setLoadUnreadable` is only called in `loadState`), so the
imported data and every workout logged afterwards are gone on reload. Receipt [measured, node + mock storage]:
```
1 loadUnreadable after corrupt load: true
1 saveState(imported) returned: false | saveFailed signal: false | stored still corrupt: {not json
```
The red banner (`App.jsx:58-61`, "Nothing you do now will be saved") is correct. But the success message
contradicts it (DESIGN §5: no ambiguity about whether something was saved), and the pre-import safety download
(`import-backup.js:44`) exports the **empty** in-memory state, not the raw corrupt value. **Needs Emilio's call:**
what recovery looks like. For example, copy the raw value to a quarantine key and then allow an import to clear the
latch, or keep refusing and say so at Import.

### F-STRUCT-6 — `storage.js` is four modules; the model↔workout-log import cycle forces a duplicate · debt · effort: days · NEW (extends F-STRUCT-4)
`storage.js` has 39 exports and 15 non-test importers [measured]. Only about 10 of them are persistence
(`getSaveFailed`…`saveState`, `:14-217`). The rest are:
- state reducers: `removeExerciseFromState`, `removeRoutineFromState`, `replaceItemInState`, `restoreExerciseInState` (`:372-437`)
- history queries: `lastSetsForExercise`, `historyPrescription`, `historySetPrefill`, `previousSameRoutineWorkouts`, … (`:483-626`)
- UI wording and labels: `deletionConfirmHead` (`:442`), `durationLabel` (`:560`)

`model.js` imports `workout-log.js`, which imports `model.js` back (`workout-log.js:2-4` documents that the cycle is
"safe under live bindings"). Because of it, `progress.js:55-59` keeps its own copy of `isSkippedSet` ("not imported:
workout-log imports model, which imports this file"). `store.jsx` still holds 10 inline reducers
(`grep -c "setState((s) => ({"` → 10) next to those moved into `storage.js`/`workout-log.js`. For Phase 2's "define
the model first", the entity rules are spread across `model.js`, `storage.js`, `workout-log.js` and `store.jsx`, with
no single place that owns the history queries.

### F-DEAD-3 — 40 legacy `session*` fallbacks can never be reached after migration · debt · effort: hours · NEW
Every load (`storage.js:181`) and every import (`exchange.js:275`) goes through `migrateState`, which strips
`sessionId`, `sessionItemId`, `sessionName` and `completedSessionItemIds` from workouts, sets, snapshot items, plans
and slots. Receipt [measured: a legacy state with `session*` keys at every level, through `migrateState(…, {legacy:true})`]:
```
legacy session* keys left after migrateState: 0
```
Yet 40 reads outside `model.js`/`exchange.js` still fall back to them [measured, grep]: `storage.js` ×12,
`workout-log.js` ×7, `history/helpers.js` ×3, and 1–2 each in 13 more files (e.g. `itemKey`, `workout-log.js:7`;
`setsForItem`, `:14-18`; `routineDeletionImpact`, `storage.js:326`). They have no effect today, but they double the
id vocabulary that a Phase-2 model change has to reason about. (`programName`/`programId` are **not** in this
count: they deliberately survive into snapshots, per BACKLOG Phase 2.)

Since v9 (req-85), these persisted fields were added without a version bump. None appears in `schema.md`, and only

### F-RISK-6 — localStorage size is a hard limit the app doesn't watch · debt · effort: days (belongs to the Phase 3 backend fork) · NEW
Each save writes the whole state (`storage.js:210`). Measured record size: **7.6 kB per workout** on `src/db.json`'s
13 real-shaped workouts (25 sets average), and **6.6 kB** for a synthetic 6-exercise, 18-set workout. Measured load
and serialize cost (node):
```
n=200   1.26 MiB  stringify 1.37ms  loadState 9.0ms   historyPrescription 0.032ms
n=1000  6.30 MiB  stringify 7.07ms  loadState 46.8ms  historyPrescription 0.036ms
n=2000 12.61 MiB  stringify 14.23ms loadState 102ms   historyPrescription 0.080ms
```
[inferred] A roughly 5 MB per-origin quota puts the limit at about 650–790 workouts, a few years at 3–4 a week.
When it's hit, every save fails behind the save-failed banner, and nothing warns before that. Snapshots are 35% of
record size in the seed data [measured]. The speed is fine (not a performance finding). This belongs with req-146.

### F-CODE-3 — "the previous workout" is chosen two different ways · debt · effort: minutes–hours · NEW
`lastSetsForExercise` sorts by `finishedAt` (`storage.js:484-486`). `previousSameRoutineWorkouts`, which feeds the
Finish "beat last time" line (`finish.jsx:53`) and the auto-complete deltas (`auto-complete.jsx:42`), relies on the
array being newest-first (`storage.js:600-605`: "`workouts` is newest-first (store.finishWorkout prepends)").
Imports keep the file's order. Receipt [measured, oldest-first array]:
```

lastSetsForExercise (same array): w-new
```
So after an import that isn't newest-first (an AI-edited file, say), the Finish comparison is made against the
**oldest** workout. The prefill still uses the newest.
