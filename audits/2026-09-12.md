## Findings (sorted by severity)

### F-CONFIG-1 — tracked grants break `plan doctor` and will leak into `main` on publish · blocks-a-plan · effort: minutes
**Introduced this session.** The planning grants were moved from the gitignored
machine-local `.claude/settings.local.json` into the tracked
`.claude/settings.json` (commit `25d7db2`), and the local file was deleted. This
diverges from the recorded model in four places and has two concrete consequences:

- **`plan doctor` now mis-reports grants as missing.** `plan:569-572` reports
  grants "ok" only if `settings.local.json` *exists*. Receipt [measured]:
  ```
  FIX: grants — no .claude/settings.local.json in the planning worktree (…).
       Re-paste the grant block from README §Setup step 5.
  doctor: one or more setup checks need attention (see FIX: lines above).
  ```
  The grants are in fact present (tracked), so this is a false failure.
- **Next `plan publish` leaks planning grants into `main`.** `main`'s
  `.claude/settings.json` is deny-only (no `allow`) [measured: `git show
  main:.claude/settings.json`]. The planning-branch commit adds the `allow` list
  (`git push origin planning/main planning`, `plan save/publish/closeout`), so
  merging `planning → main` hands the **code worktree** exactly the commands
  DEC-005/DEC-026 and CLAUDE.md forbid it from running. A grant only suppresses a
  prompt (it doesn't make code CC run them), but it removes the re-prompt
  guardrail — a trust-model regression.

Contradicted docs: `README.md:64` (setup step 5 writes `settings.local.json`,
"gitignored by design — recreate on every machine"); `DEC-005` and `DEC-026`
(grants live in machine-local `settings.local.json`); `NOW.md:25` ACTION
("re-paste planning `.claude/settings.local.json`") — now moot, the file is gone.

**Disposition is Emilio's** (it reconciles decisions, not code): either record a
superseding DEC that intentionally tracks the grants — and then reconcile README
§Setup step 5, `plan doctor`'s grant check, DEC-005/026, and the NOW ACTION — or
revert to the machine-local model. Do not `plan publish` until this is settled.

### F-RISK-2 — a corrupt or non-JSON `workout-mvp-v8` value silently loads as empty, then is overwritten · bug · effort: hours
`storage.js:64-80`: `loadState` does `JSON.parse(raw)` at `:68`; any parse throw
falls to the blanket `catch` at `:78` returning `emptyState()` —
indistinguishable from a blank device. `store.jsx:11` seeds state from that, and
the **first** mutation's `saveState` writes empty state over the corrupt key. Net:
one corrupt byte discards all history, no banner, no legacy-key fallback (req-06
has already removed them in steady state). The `catch` can't tell "corrupt" from
"empty," so nothing can warn. Evidence: no test seeds a non-JSON `v8` value
(grep of `storage.test.js` shows only valid-JSON seeds). Low probability
(setItem is atomic; vectors are tampering/disk/browser-bug), total loss.

### F-RISK-1 — the `v5` migration path has no round-trip test · bug · effort: hours
`storage.js:5` lists `workout-mvp-v5` in `LEGACY_KEYS`; `SHIPPED.md:131` claims
`v7/v6/v5 → v8` all work. But v6 (`storage.test.js:107-158`) and v7
(`:164-227`) each have a seed-and-upgrade test, while v5 has **only** a
delete-assertion (`:182`) — no test seeds a v5-shaped payload and asserts a clean
upgrade. This violates CLAUDE.md's migration ask-gate ("add a migration test that
proves an older key survives the upgrade") for one of three supported versions.
Compounded by F-DRIFT-2: the v5 on-disk shape is undocumented, so it must be
reconstructed from git history before a test can be written.

### F-RISK-3 — no cross-tab sync; two open tabs are last-writer-wins over the whole key · bug · effort: hours–days
`store.jsx:13-19` + `storage.js:83-92` serialize and write the *entire* state; no
`storage`-event listener exists (grep for `addEventListener('storage'`/`onstorage`
across `src` → none). Reproduction: open tab A and tab B (each `loadState` reads
history H). Finish a workout in A → A persists `H+A`. Finish another in B (still
holding H) → B persists `H+B`, clobbering A's workout, no warning. Plausible on
desktop where tabs stay open.

### F-CODE-1 — the same workout yields two different forward recommendations by code path · bug · effort: hours
The progression computation (filter an item's working sets → `recommendNext­Prescription`)
exists twice with **divergent set-matching**:
- `model.js:297-324` (`progressionFromWorkout`, used by `store.recalculateFuturePlans`)
  matches via `set.routineItemId || set.sessionItemId`, falling back to `item.id`,
  with a `String(set.reps || '')` skip guard.
- `finish.jsx:30-61` (inline, this is what's actually **saved** at Finish) matches
  via `set.routineItemId === itemKey(item)` only — no `sessionItemId`/`item.id`
  fallback, and `String(set.reps)` without the `|| ''` guard.

So the recommendation written at Finish can differ from the one a later
"recalculate future plans" produces on the *same* workout, for any set that
matches only via a fallback path. This fails DESIGN §2's explicit test — "given
the same history, does the recommendation always produce the same explainable
step?" Fix is one shared helper returning the core `{sets, recommendation}`.

### F-CODE-2 — `performedOn`/`plan.date` stamped in UTC while everything else uses local time · bug · effort: minutes
`store.jsx:214` and `:233` build the day key inline as
`new Date().toISOString().slice(0,10)` (**UTC**), stamped onto `plan.date` and
`activeWorkout.performedOn`. The canonical `dateKey` (`schedule.js:15-21`) — used
by `workout-actions.js`, `storage.js` (`completedOnDayKey`), Start, Settings, and
all schedule matching — is **local** time. Near midnight for any user behind/ahead
of UTC these disagree: a workout finished in the evening (Americas) gets a
`performedOn` of *tomorrow*, misdating the persisted record and its day grouping.
`workout-actions.js:6` already uses `dateKey(new Date())` for this — the store
paths are the outliers. Route both through `dateKey`.

### F-RISK-4 — a malformed backup (non-array `workouts`/`slots`) throws a raw `TypeError` · debt · effort: minutes–hours
`exchange.js:141-153` (`unwrapBackup`) only checks `payload.state &&
typeof payload.state === 'object'`; it doesn't array-check inner fields before
they are `.map`ped in `model.js:263`/`:232`. Measured reproductions:
`{kind:'workout-mvp-backup',version:1,state:{workouts:'oops'}}` →
`TypeError: (source.workouts || []).map is not a function`; same for
`state:{schedule:{slots:'x'}}`. **Not data loss** — import sites catch it
(`Today.jsx:175`, `Settings.jsx:61`) and the pre-import safety backup already
fired (`import-backup.js:37`) before the throw — but the user sees
"map is not a function" instead of "Not a workout database backup."

### F-DIV-1 — recommendation invents a 0.5 kg step when the exercise has no valid increments · debt · effort: hours
`progress.js:28`: `moveToValidWeight` falls back to
`Math.max(0, Math.round((current + direction*0.5)*2)/2)` (a hardcoded ±0.5 kg)
when `validWeights()` is `[]`. Reachable for a `machine`/`free` exercise with
`weightStep:'n/a'` (the `addExercise` default, `store.jsx:172`) and a logged
weight: it hits the weighted-adjust branch (`progress.js:80-88`) and recommends a
step the exercise config never defines. Narrow but real — the load can't be
traced to a valid increment (DESIGN §2 / README recommendation rules). Needs a
behaviour call (hold vs. a documented default step) then a unit test.

### F-DIV-3 — "referenced → archive" is implemented as referenced-by-history-only · debt · effort: minutes (doc) / hours (if broadened)
`store.jsx:44-67` (`removeRoutine`) and `:185-204` (`removeExercise`) test
`referenced` against `s.workouts` (finished history) **only**. A routine
referenced solely by a schedule slot or a planned (not-yet-performed) workout is
hard-deleted, and its slots/plans are silently removed in the same write
(`:56-64`), behind a `Delete {name}?` confirm that doesn't mention the slots
(`Routine.jsx:150-158`). The DESIGN §3 rationale ("history keeps pointing at what
it recorded") supports the history-only reading, so this is likely intentional —
but the literal word "referenced" reads broader. Worth a DEC to pin down.

### F-DIV-2 — the prefill docs understate the sanctioned DEC-002 kg carry · debt · effort: minutes
`workout-log.js:183-191` (`setLogSeed`) + `item.jsx:116-124` (`carryFor`) +

## Performance — measured, no finding

The suspected N-log-N hot path is `lastSetsForExercise` (`storage.js:198`), which
copies + sorts **all** finished workouts per call and runs up to 2× per render of
the live set-log screen (`item.jsx:175,385`) plus once in the routine editor
(`Routine.jsx:328`). Benchmarked in Node over synthetic history (4 exercises ×
3 working sets per workout), 2000 iters/case [measured]:

| history size | `lastSetsForExercise` | simulated `item.jsx` render (2×) |
|---|---|---|
| 200 workouts | 0.005 ms | 0.010 ms |
| 1,000 | 0.026 ms | 0.053 ms |
| 5,000 | 0.126 ms | 0.249 ms |

At a realistic single-user history (~200 workouts) the per-render cost is ~0.01 ms;
even at 5,000 workouts (a decade of daily training) it is ~0.25 ms. **Not a
finding.** If history-scanning selectors multiply in future screens, revisit — but
today the "sort all history on every render" shape is harmless.
