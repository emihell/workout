## Findings (sorted by severity)

### F-SYNC-1: the three-way merge can leave a finished workout in progress, which leads to duplicate workout ids · bug · effort: hours · NEW

- **The cause.** `mergeStates` (`src/sync/merge.js:112-131`) treats `activeWorkout` as one record. `finishedState` keeps the active workout's id on the finished record (`src/workout-log.js:220-245`).
- **The trigger.** Device A finishes the workout. Device B, on the same base, edits the in-progress workout (logs a set) before it pulls. When B pushes, the merge sees `activeWorkout` edited on both sides, so incoming wins. `workouts` keeps A's finished record.
- **The result.** The same workout is both in progress and in history. `mergeWithoutBase` already guards this exact case (`merge.js:190-194`, "a finished workout can't be in progress", DEC-133 round 5). The three-way path has no such guard.
- **The validator doesn't stop it.** `validState` → `applyBackup` (`server/store.mjs:27-47`, `src/exchange.js:579-590`) accepts duplicate workout ids. That validator is also the local Import's.
- **What follows.** `idCollection` returns null on a duplicate id (`merge.js:29`), so every later merge treats `workouts` as a single record.

Receipt [measured, a probe script against `src/sync/merge.js`, `finishedState` and `server/store.mjs validState`; base = an in-progress `wo-1`; A = `finishedState(base)`; B = base + one more set]:
```
merged activeWorkout.id: wo-1 | workouts ids: [ 'wo-1' ] | conflicts: [ 'activeWorkout:edited-on-both' ]
server validState accepts it: yes
after second Finish, workouts ids: [ 'wo-1', 'wo-1' ]
validState accepts duplicate ids: yes
next merge (A edits a note, B finishes wo-9): workouts ids: [ 'wo-1', 'wo-1' ] conflicts: [ 'workouts:edited-on-both' ]
```
In that last merge, B's finished `wo-9` is not in the result. It survives only as the `lost` value of a conflict on the server.

In the app [inferred from the code]: `workoutUpdatedState` and `workoutRemovedState` (`src/state-reducers.js:489-493`) match by id, so a History edit or delete of one copy hits both.

- **Context.** DEC-143's addition ("its on you if you edit on multiplate devies") accepts newest-wins losses for one user. This goes further: it corrupts the record's shape and stops per-id merging for good.
- **Not covered by the existing backlog item.** BACKLOG §Phase 3 "Before a second user logs in" lists the losers-not-recorded gap, but not this.
- **Fix shape:** the no-base-finished guard, or an id-uniqueness check in the validator. Changing the merge is shared code, and repairing existing data would be ask-gate #2.

### F-SYNC-2: whole-state sync makes server storage and upload grow quadratically with history · debt · effort: days (needs a decision) · NEW (absorbs 09-24 F-RISK-6, still untracked)

- **What gets sent and stored.**
  - Each save marks the state dirty, and a PUT follows 2 s later (`src/sync/engine.js:366-375`, `DEBOUNCE_MS` `:48`). The set-form draft is saved 300 ms after typing stops (`DRAFT_WRITE_MS`, `workout-log.js:781`), so each logged set causes at least one push.
  - Every push sends the whole state (`engine.js:291`).
  - The server stores each accepted push as a full revision (`server/store.mjs:206-208`).
- **What is kept.**
  - Pruning keeps all revisions from the last 14 days, then the newest revision of each day **forever** (`store.mjs:256-272`; DEC-141 §3 records the policy, not its growth).
  - `./server/deploy` takes a full DB backup `deploy-<sha>` on every deploy (`server/deploy:15-17`). Rotation deletes only scheduled backups: "other backups (deploy, pre-restore, by hand) are never deleted here" (`server/ops.mjs:133-149`).

Measured cost per push, with `src/db.json` workouts cloned to size [measured, probe script, `:memory:` DB]:
```
n=24   state  193 kB | server putState fast-forward   3.7 ms | mergeStates  0.5 ms | client per-save norm+deepEqual  0.9 ms
n=200  state 1500 kB | server putState fast-forward  26.5 ms | mergeStates  2.4 ms | client per-save norm+deepEqual  6.6 ms
n=1000 state 7442 kB | server putState fast-forward 140.4 ms | mergeStates 12.1 ms | client per-save norm+deepEqual 37.9 ms
```

Projection [inferred from those sizes, 3.5 workouts a week, at least one daily revision kept per workout day]:

| | ~1 year (200 workouts) | ~3 years |
|---|---|---|
| upload per logged set | ~1.5 MB | ~4 MB |
| upload per 25-set workout | ~40 MB | ~100 MB |
| daily revisions kept on the server | ~150 MB | ~1 GB |
| deploy backups | each is a full copy of that DB | each is a full copy of that DB |

- **The phone's own limit (09-24 F-RISK-6).** localStorage still holds the whole state and has a roughly 5 MB quota, so the limit is around 650 workouts. Nothing warns before it is hit. When it is, `saveState` fails behind the banner, and sync then holds the only current copy (`persistence.js:345-350`).
- **The server's limit.** The 20 MB body cap (`engine.js:50`, `app.mjs:59`) is reached at about 2,700 workouts.
- **Not urgent.** Today's size (24 workouts) is fine. It is a design limit, and it belongs with the stage-2 sync work.
