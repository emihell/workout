## Technical

**What changed**
- `server/plan.mjs` (new): `readPlanFile` (the app's Export or a bare state → `validState`), `planChange` (pure:
  `keptHistoryState` → `validState`, refusals, the import's `previewLines(importPreview(…), 'keep')`, counts),

- `server/store.mjs`: `putState(db, userId, body, at, {source, note, fastForwardOnly})` — the 5th argument is new;
  the HTTP route passes nothing, so device pushes store null. `listRevisions`/`getRevision` return `source`/`note`.
  `pruneRevisions` skips `source IS NOT NULL`. `revisionRow` is now `SELECT *`, so a read-only handle on a DB that
  predates the columns can still read it.
- `server/README.md`: the three commands plus a "Plan changes" section. `server/app.mjs`: header comment only.

**Domino check.** `putState` is shared with `PUT /api/state`. The new argument defaults to the old behaviour.
`revisionId` hashes `rev|created_at|state` and is unchanged, so every existing rev id still matches. Pruning only gets
more conservative. All 87 server tests that existed before pass unchanged (the first run's "100" counted the 13 new ones too).

**Choices the spec left open**
1. **"A file whose workouts differ → refused"** — I read this as "the file would change history". A record the file
   has that the server lacks, or holds differently, is refused. A record only the server has (logged after the export)
   is allowed, because Keep my history keeps it. Read strictly instead, any coach file made before the newest logged
   workout would be refused, and the plan "continuously changes". *(unconfirmed, behaviour)* It is a single function,
   `historyMismatch`.
2. **The preview lines** are `previewLines(importPreview(current, file-with-the-server's-history), 'keep')`. Written
   that way, "Logged history" and "Workout in progress" describe what this write does (unchanged). Fed the raw file,
   they would describe Replace's history diff.
3. **A plan file must carry `exercises` and `routines` arrays.** `validState({})` accepts an empty object as an empty
   state, and applying that would archive or drop the whole plan.
4. **Revert refuses during a live workout**, the same as apply. Revert does not compare the reverted revision's history,
   because that revision is older by design.
5. **Fast-forward only.** The write goes in only from the previewed rev. If a device pushed in between, the write
   returns 409 and its backup is deleted. The spec's "one transaction" can't hold the backup, which is async and
   outside the transaction, so the backup comes first and the rev check sits inside `putState`'s transaction.
6. **Revert revisions are kept by pruning too** (`source IS NOT NULL`), not only apply revisions.
7. **Names:** `--source` is 1–28 characters `[a-z0-9-]`, so that `before-plan-<source>` fits the backup-reason limit,
   and `revert` is reserved. `--note` is required for apply and optional for revert (default `revert to rev N`).
   `--user` is needed only when the DB has more than one account. Without `--yes`, apply/revert exit 2, the same as
   `restore`.
8. **Preview opens the DB read-only.** It never even adds the columns. SQLite leaves empty `-wal`/`-shm` sidecars;
   `workout.db` itself is byte-identical.

## Review fixes (round 1: no blockers)

1. **`--yes` is tied to the approved preview.**
   - `apply --yes` and `revert --yes` now require `--expect-rev <n>`.
   - If the current rev ≠ n, the command prints `REFUSED: The server is at rev X, not the previewed rev n.` and exits 1,
     with nothing written and no backup.
   - The dry run ends `To write it: … --yes --expect-rev <n>`.
   - Implemented as `applyPlan`/`revertPlan` `expectRev`. The check runs before the backup.
   - Test "review 1": a missing flag → exit 1; a stale rev on both apply and revert → exit 1, rev unchanged, 0 backups;
     the current rev → `wrote rev 3`.
2. **A file without an `anchor` keeps the server's.**
   - `withCurrentAnchor` runs in `planChange` before `keptHistoryState`. A file with an anchor still sets its own.
   - Test "review 2": `2026-09-28` is kept; the file's `2026-10-05` replaces it.
3. **Deploy order.**
   - README "Plan changes" now opens with **Deploy first** and says why: an old server's pruning would drop the plan
     revisions.
   - When `WORKOUT_DATA_DIR` is the live data dir, `--yes` refuses unless `ops.liveBuildCheck` confirms that the sha in
     `<live>/DEPLOYED` contains `server/plan.mjs`. The check is `git cat-file -e <sha>:server/plan.mjs`, tried in
     `WORKOUT_REPO_DIR`, this checkout, then `~/dev/workout/workout-codebase`. A non-live dir skips it.
   - Test "review 3", on a temp git repo:
     - no DEPLOYED → no
     - a sha before plan.mjs → no
     - a sha with it → yes
     - an unknown sha → no
     - garbage → `names no commit`
   - `[inferred]`: the CLI path on the real live dir is not run, because it would point at the live install (BACKEND rule 2).
4. **`addRevisionColumns` tolerates a concurrent ALTER.** It catches `duplicate column name` and re-checks
   `table_info`. Not tested: two processes would have to race between the check and the ALTER.
5. **`plan preview` exits 1 when it prints REFUSED.** Test "review 5–7".
6. **Dry runs run `checkMeta`.** `apply` without `--source` or `--note` → exit 1, even without `--yes`. Test "review 5–7".
7. **A plan file with zero routines is refused** (`Not a workout plan: the file has no routines.`). Test "review 5–7".
8. **Corrected the test count.** The first round's "100" was 87 existing + 13 new tests.
