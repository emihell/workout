# req-248 — a hanging test turns the gate red instead of hanging it

## Technical

**Measurement (2026-10-26):**
- Slowest single test: 5231 ms locally ("none of the 578 hidden entries appears…") and 2898 ms on CI (run 40367239914).
  Taken from TAP `duration_ms`: `WORKOUT_SERVER_TEST=1 node --test --test-reporter=tap <all files>`, 2108 tests.
- Slowest hook: `src/sync/builds.test.js`'s `before` (two vite builds) took 1258 ms under full-suite load.
  Measured with a temporary `Date.now()` stderr line, then reverted.
- Whole test step: 80–105 s locally (288 s once under load), 96 s on CI.
- So N = 3 × 5.2 s, rounded up → **`--test-timeout=20000`**.

**Do timeouts cover hooks?** Yes. Probes run with `node --test --test-timeout=1500`: a never-resolving top-level
`before` → fail, "test timed out after 1500ms", 2 s. A never-resolving `before` inside `describe` → cancelled, 2 s.

**Two gaps the spec didn't anticipate, both found by probe:**
1. **A timed-out test that leaves a timer open keeps its file's process alive.** It's marked cancelled, but the run
   never ends. Probe (`setInterval` + never-resolving promise): still running after 2 min. Adding
   **`--test-force-exit`** makes it exit 1 in 1 s.
2. **req-239's actual hang is synchronous.** The hung `req-10.test.js` child was at 178% CPU and 3 GB RSS 25 s in (`ps`).
   A render loop never yields, so no in-process timer can fire. With both flags it was still running at 90 s.
   The fix is a **watchdog in `./check`** around the `node --test` step. Past 900 s (~3× the slowest full run
   measured, 288 s) it prints the still-running test files (the child processes' last argument), then TERMs/KILLs
   them, and the gate fails. `WORKOUT_TEST_LIMIT` overrides the limit and says so on stderr; it exists only to prove
   the watchdog fires. Bash 3.2-safe, `pgrep`/`pkill` on macOS and Ubuntu. The watchdog polls once a second, so it
   leaves no orphaned `sleep` holding a pipe.

`deploy.yml` job `check`: `timeout-minutes: 10` (~3× the 2m03s green run). On CI a synchronous hang hits this before
the 900 s watchdog; the comment says so.

## Workflow

- **Scope added: `--test-force-exit` and the 900 s watchdog.** The spec's `--test-timeout` alone would not have caught
  req-239's hang (synchronous) or a cancelled test that keeps a timer open. Both were shown by probe before I added
  anything. The watchdog bounds the whole step, so it isn't a per-file timeout (out of scope). Tooling only;
  nothing Emilio sees changes.
- **`WORKOUT_TEST_LIMIT`** is a new env knob. It can loosen the gate as well as tighten it, so it's echoed on stderr,
  like `WORKOUT_SKIP_CHECK`. If Planner would rather not have it, drop it; the watchdog proof would then take 15 min.
- **Correction to my req-239 report:** I wrote that the rendered suite "hangs" under the mutation as though the cause
  were test plumbing. It's an app-side synchronous render loop (CPU-bound, memory climbing), which is why no
  `--test-timeout` stopped it.
- **Also seen:** under `--test-force-exit`, a file whose rendered suite was stuck reported 12 fewer tests (2096 of
  2108) and was neither failed nor cancelled. The gate was red that time because of a unit-test failure. Candidate L-:
  "tests N" dropping below the known count is a signal too.
- **Candidate L-:** an in-process timeout can't stop a synchronous loop; only an outside watchdog can.
