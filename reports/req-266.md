`lib/internal/test_runner/test.js:1102-1126`, the force-exit branch calls `process.exit()` once the reporter stream

## Technical

- **`check`**: dropped `--test-force-exit` from the `node --test` line and rewrote the req-248 comment block. Each test
  file's process now exits on its own once its output is written, so nothing gets cut off.
- **req-248's guarantee holds without force-exit.** On node 22.23 the runner applies `--test-timeout` to each FILE
  as well: it spawns the child with the file's abort signal (`runner.js:376-386`), so a file still alive at 60 s is
  killed and reported `✖ <file> test timed out` (AC2 receipts). req-248 saw a held file run past 2 min without
  force-exit. [inferred] That was an older node: L-065 records nvm's default 22.14 under `plan publish`. Not re-measured.
  The 900 s watchdog is unchanged, and it is still the only thing that stops a synchronous hang (receipt above).
- **`src/test-support/long-timers.js`** (new): `catchLongTimers()` wraps `globalThis.setTimeout` and records timers
  of 10 s or longer until `release()`, which clears the ones still pending. **Test edit, called out:**
  `src/req-203.test.js` §4 and `src/req-220.rendered.test.js` (Export for your AI) call it around their Export click
  and release it in their existing `finally`. That is setup only. No assertion changed, and app code is untouched.
- **Choice the spec left open:** a test that **passes but leaves a handle open** is now red: its file is killed at
  60 s (the `zz-req266-leak` probe). Under force-exit it was green. That is stricter, and it is the literal reading of
  AC2. Cost: a future rendered test that clicks a download without `catchLongTimers` fails after 60 s with
  "test timed out" on the file. The `check` comment names the helper.
- **Rejected alternative (built, measured, then removed in `24bd393`):** keep force-exit and preload a script
  (`--import`) that sets the children's stdout pipe to blocking (`process.stdout._handle.setBlocking(true)`).
  It also gave 10/10 at 2187, plus 12/12 under 2× parallel load. I dropped it for three reasons:
  - it depends on a private `_handle` API, so a node upgrade could silently bring the bug back;
  - it kept leaked handles green;
  - it cost about 1 s per `./check` (9.8 s vs 8.8 s).
- **Not changed:** the zero-test guard, the TAP file and the watchdog.

## Workflow

- The branch history shows the rejected route: `0319c86` adds `scripts/test-stdio-blocking.mjs`, and `24bd393`
  removes it. Squash at merge if a clean history is preferred.
- The spec's numbers matched, except one: main runs ~8 s here, not the 80–105 s in req-248's comment (that comment
  is left as it was, since it records req-248's measurements).
- Candidate L- (for Planner): `--test-force-exit` drops results that are still queued on the stdout pipe. A child that
  exits 0 with lost output passes as `ok`, so lost tests never show as red. Ending a process with `process.exit()`
  while it still writes to a pipe loses data on POSIX.
- Candidate rule: a rendered test that triggers a download wraps it in `catchLongTimers()`.
- QA: no UI change, so the test list is the probes above. Smoke ran through `./check --smoke` on HEAD's own build
  (isolated port), not through `./plan qa`.
