# req-119 — setup edits never reach into the live workout (audit B)

Branch `req-119`. Ready to look at, not merged. Touches the store delete paths and adds one optional snapshot-item field, so per DEC-057 the reviewer and the backup reminder come before merge.

## Technical

**What changed**
- `storage.js` (pure, tested):
  - `exerciseInActiveWorkout` (snapshot item or logged set uses it) and `routineInActiveWorkout` (`routineId || sessionId || snapshot.routineId`).
  - `removeExerciseFromState` / `removeRoutineFromState`: the reducers moved out of `store.jsx`. "Referenced" = finished history (DEC-031, same tests as before via `exerciseDeletionImpact` / `routineDeletionImpact`) **or** the active workout (DEC-058 §5) → the existing `archivedAt` path. All other side effects are unchanged (strip from routines and plan items; drop schedule slots and plans). `activeWorkout` is never touched.
  - `deletionConfirmHead(name, { hasHistory, inCurrentWorkout })`: the confirm head line.
  - `isFirstRun(state)`: no routines, no workouts, no active workout.
- `store.jsx`: `removeExercise` / `removeRoutine` call the reducers.
- `Exercises.jsx` / `Routine.jsx`: the confirm uses `deletionConfirmHead`. The "This removes …" tail is unchanged.
- `Today.jsx`: `if (isFirstRun(store))` replaces `if (!routines.length)`. TodayEmpty comment updated.
- `model.js` `buildPlannedWorkout` and `workout-log.js` `replacementItem`: each item gains `hasDuration: Boolean(exercise?.hasDuration)`.
- `workout-log.js` `sessionExercise(live, item)`: `item.jsx`'s `liveExercise` now delegates to it. When the item has `hasDuration`, name, equipment, type and Timed come from the snapshot. id, weightStep, cues and durationSec stay live. When the item has no `hasDuration` (a workout started before this build), it returns exactly the old result (`live || fallback`). `completeSet`'s `ex.type`, `weighted`, `repsLabel`, `showEffort`, `timedSet`, `setPreview` and `durationTargetFor` all read this `ex`.

**Persisted data:** one optional snapshot-item field, `hasDuration`. No schema bump and no bulk write. It is written only when a workout starts or an item is replaced. `migrateState` → `workoutSnapshot` keeps it through `...rest` (tested with a reload). `exchange.js` checks only that snapshot items are objects.

**Dependents checked**
- `removeExercise` / `removeRoutine`: only callers are the Exercises and Routine delete buttons. Unreferenced objects are still hard-deleted (tested). `storage.test.js` impact tests pass unchanged.
- `liveExercise`: WorkoutItemLive (form, preview, completeSet) and WorkoutItemDone (title, equipment). The title's Library link still resolves because `ex.id` stays live (tested).
- `buildPlannedWorkout`: store `getPlannedWorkout` / `startWorkout`, `overview.jsx` preview, and the model / skip-replace / finish-routine / req-116 / req-117 / routine-item-parse tests. The field is additive and every existing test passes.
- `replacementItem`: `store.replaceItem`. Mid-workout items are kept as-is by `workoutSnapshot`.

**Open choices (unconfirmed)**
- Confirm wording: "`<name>` is in the current workout and will be archived (the workout keeps it)." This wins over the "has past workouts" line when both apply.
- Name and equipment come from the snapshot mid-workout. **durationSec stays live**: the task allowed only one new field, and a snapshot `durationSec` would be a second one. Item `durations` (from the routine) still take precedence as before.
- An item without `hasDuration` falls back to the whole live exercise (the old behaviour), not per field. So a workout already in progress at deploy keeps the old bug until it finishes.
