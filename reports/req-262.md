## Technical

- **Part 1.** `src/state-reducers.js` `slotSwappedOnDateState` takes `today`, which `src/store.jsx` `swapSlotOnDate` sets to `dateKey(new Date())`. The reducer drops swaps whose date key is earlier than `dateKey(mondayOf(today))`.
  - With no `today`, or one that isn't `YYYY-MM-DD`, nothing is pruned. The reason: `'NaN-NaN-NaN'` would sort after every date key, so every swap would be dropped.
  - A swap that changes nothing still writes the pruned list when there was something to prune. With nothing to prune it returns the same state object, as before (req-225's identity tests still pass).
  - `normaliseSwaps` and the load path are untouched.
- **Part 2** (final form, after Planner's call): in `src/model.js`, `progressionForItem` for an item whose exercise type is `cardio` now does two things:
  - It returns the snapshot item's own `to`/`targetsTo`, the same as when no sets are logged.
  - It returns `writesRoutine: false`, and `progressionFromWorkout` drops those entries. So `applyProgressionToRoutines` never touches the routine item: the test asserts the very same object, not just equal content.
  - Any `progressionForItem` caller that compares the whole returned object would now see the extra field. The full suite is green.
- **Part 3.**
  - `src/current-workout.js` `finishedForPlan(workouts, plan, now, { finishedHere })`: on the ad hoc fallback, a same-routine workout with `id === finishedHere.id` covers the plan within 6 h of `finishedHere.at`.
  - `src/store.jsx` keeps `finishedHere = { id, at }` in `useState` (memory only). `finishWorkout` sets it from `state.activeWorkout.id` and `Date.now()`.
  - `src/views/workout/overview.jsx` passes `store.getFinishedHere?.()`.
- **Part 4.** `src/workout-log.js` `setsForItem`: the key comparison runs only when the key isn't `''`, and the `item.id` comparison only when `id != null`.
- **Choice the spec left open: the store exposes this as `getFinishedHere()`, not as a `finishedHere` field.** The Settings export calls `exportBackup(store)`, and `buildBackup` → `dataOnly` keeps every non-function field. A plain field would have been written into backup files. The test asserts that both `localStorage['workout-mvp-v9']` and `buildBackup(store)` lack it.
- **Planner's decision (round 2): cardio Apply leaves the routine item untouched.** Apply writes neither `suggestedWeights` nor `targets` for a cardio exercise.
  - Round 1 instead wrote back the snapshot item's own values, which is the spec's literal wording.
  - With that version, old cardio snapshots that already hold `suggestedWeights: [0]` still wrote `[0]`. All 13 in `db.json` do, and so may real data from before this fix.
  - Related: `./plan qa --seed` loads through the v8 legacy path, which rebuilt my seeded `[]` snapshot as `targets ["5-8 min"]`, `[0]`. That's why AC5 injects into v9 instead.
- **Behaviour change for keyed items in `setsForItem`.** Before, an item with a `routineItemId` but no `id` also matched every set with no `routineItemId` (`undefined === undefined`), whatever its exercise. Now such sets match by `exerciseId` only, which follows the spec's "item.id only when defined".
  - Callers, unchanged otherwise: `routine-update-offer.js:36`, `finish-unfinished.js:25,34`, `workout-log.js:153,364,369,473,853,1108,1116,1167`. The full suite is green.
- **Test edit:** `src/views/workout/overview.test.js:62`. The source-guard regex pinned the old exact call `finishedForPlan(store.workouts, plan)`; it now pins the new call with `finishedHere`. Nothing weakened.
