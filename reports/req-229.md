API: `GET /api/health` → `{ok, revisions}`; `POST /api/register {code, username, password}`; `POST /api/login`;
`POST /api/logout`; `GET /api/me`; `GET /api/state` → `{rev, state}`; `PUT /api/state {baseRev, state}` →
`{rev, state, merged, conflicts[, unchanged]}`; `GET /api/revisions`; `GET /api/revisions/:rev` (state + full
conflicts); `GET /api/export`; `GET|POST /api/notes`.

CSRF guard on every non-GET (login/register/logout included): header `X-Workout-Request: 1` required (cross-site
needs a preflight, which the server never answers); `Sec-Fetch-Site`, when sent, must be `same-origin`/`none`;
`Origin`, when sent, must equal `Host` or `X-Forwarded-Host`; `Content-Type: application/json` else 415.

Merge (`server/merge.mjs`): top-level arrays whose elements all have a unique `id` merge per id; anything else
(schedule, activeWorkout, legacyRecommendations, schemaVersion, an array without unique ids) is one record. Per
record: same on both → that; changed on one side → that side (deletion = change); changed on both → incoming wins,
`{field, id, kind, lost}` pushed to `conflicts` (`lost: null` = the current side had deleted it). The merged state
is re-run through `applyBackup` before storing; the conflicts are stored on the revision row.

### Choices the spec left open (for DECISIONS)

1. **Stored state = `applyBackup(…).state`**, not the raw body — the criterion-2 "deep-equal after applyBackup"
   reads that way. Consequence for req-230: `applyBackup` drops `activeWorkout.stopwatch` (req-194) and defaults a
   missing `schedule.anchor` to this Monday; a running cardio stopwatch therefore doesn't survive a round trip
   through the server. **Flag for req-230** — likely wants the device to keep its local stopwatch.
2. **baseRev 0 against a non-empty account** merges with base = `emptyState()` (everything is an "add" on both
   sides; same-id differing records → conflict, incoming wins). req-230's first-sync flow should decide whether
   that is what it wants.
3. **No-op PUT stores nothing**: if the result deep-equals the current state, returns the current rev with
   `unchanged: true` (else every sync-on-open would mint a revision).
4. **baseRev ahead of the server → 409**; non-integer/negative → 400.
5. **Merged array order**: the incoming array's order, with current-only additions inserted after their nearest kept
   predecessor in the current array.
6. **Conflict record** = `{field, id, kind, lost}`, `kind` ∈ `edited-on-both | edited-vs-deleted |
   deleted-vs-edited | added-on-both`; the winner is the revision's own state.
7. **Sessions**: 90 days, sliding (each authenticated request extends). **Invites**: one-use, 7 days.
   **Username**: lower-cased, `[a-z0-9][a-z0-9._-]{0,31}`. **Password**: ≥ 8 characters — user-visible
   (behaviour) once req-230 has a register screen; confirm with Emilio.
8. **Notes**: `POST` takes one note or `{notes:[…]}` (so a device can re-send its list); returns `{added, total}`;
   `GET` order = arrival order. Dedupe is per user on `timestamp`+`text` (a UNIQUE index).
9. **Health** = `{ok, revisions}` (total revision count, no per-user or user-count detail).
10. **Body limit** 20 MB → 413. **Bootstrap** refused once any user exists.
11. **The `secret`** is the HMAC key for session-token and invite-code hashes.
12. **Repo-tree refusal** also refuses a data dir under *any* ancestor holding `.git` (catches other worktrees,
    e.g. `workout-codebase` when running from `workout-live`). `~` and `~/dev` have no `.git` today
    [measured: `ls -a ~ ~/dev | grep -x .git` → nothing], so the live path passes.
