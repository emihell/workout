## Technical

- **`server/plan-build.mjs`** (new, pure): `buildPlan(current, changes, {library, makeId, now})` returns `{state, file, plan, lines, warnings, refusals}`. It works in four steps:
  1. Resolve references: by id, then by a ref defined earlier in the file, then by exact name among non-archived records.
  2. Run the ops on a clone of the state.
  3. Run C3–C6 on each item the file added or changed, C3 on every slot, then C1 and C2.
  4. Run C7: `readPlanFile(buildBackup(state))`, then C1/C2 again on the file as read, then `planChange(base, file, {archivedAt: now})`.

  It reuses the app's own code: `exerciseFromData(catalogItemToExercise(entry), id)`, `pickerItem` passed through `routineItemAdded` for a new item's shape, `historyPrescription`, `isDurationTarget`, `ROUTINE_ROLES`, `uid`, `buildBackup`, `readPlanFile` and `planChange`. None of them is re-implemented. `onlyNamedChanged(base, result, named)` is exported for the AC3 self-test.
- **`server/ops-cli.mjs`**: adds `plan build <changes.json> --out <file> [--user <u>]` and its usage line. It refuses an existing `--out` before it reads anything. It opens the DB with `DatabaseSync(…, {readOnly: true})`, the same way `preview` does, and reuses `pickUser` and `printPlan`. It writes the file with `flag: 'wx'` only when there are no refusals.
- **Confirmed by a test** (the spec marked this [inferred]): a rebuilt item with a fresh id loses its logged sets. In `groupSetsByExercise`, the fresh id's group is empty.

**Choices the spec left open:**
1. **C4 `targets` count:** the spec says targets need exactly `sets` entries. I require that only for a strength item. A timed or cardio item may have empty `targets`, because `pickerItem`'s own starting plans for those have `targets: []`, and the literal rule would refuse the app's own add path. If such an item has targets, the count must still match.
2. **C3–C6 run only on items this file added or changed.** An item that was already in the base and stays untouched is not re-checked, so one odd old item can't block every plan. Slots are all checked.
3. **`item.set` refuses** when the routine holds the same exercise twice. The refusal names the item ids and says to use `routine.items`. The spec has no field to pick one of the two.
4. **`schedule.set` slot `week` is 0-based**, as stored (`fullState` has `week: 0`). The spec's example `"week": 1` is valid only with `loopWeeks: 2`. Allowed ranges: `loopWeeks` 1–4 (the range `clampLoopWeeks` allows), `weekday` 0–6 (0 = Sunday).
5. **C2 and moves/swaps:** a move or swap whose slot `schedule.set` removed may disappear. The model drops it when it normalises. Any other move or swap change, or any anchor change, is refused.
6. **Refusal order:** an op that fails is skipped, and the other ops still run, so one run reports every resolution and field error. C3–C7 run only if every op succeeded.
7. **`exercise.add`:** a `mergedInto` entry is refused with its target named. A `hidden` entry with no target is refused as hidden. `lightestWeight` and `unilateral` are set after `exerciseFromData`, which doesn't carry them.
8. **`routine.add` focus** defaults to `Machines`, as the store's `addRoutine` does, and the routine gets `archivedAt: null`.
