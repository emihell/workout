# req-161 — unreadable-state copy follow-ups

Branch `req-161` (`497de37` is the work, then this report). **Lane: data** (DEC-086): the reviewer and Emilio's eyes come
before merge.

**Writes:** only on a *confirmed Import in the unreadable state*. It adds at most one new copy key per workout key
present (v9, v8, v7, v6, v5, so 5 at most). It rewrites or deletes no existing key, has no schema change and no
migration. A retry with identical content writes 0 keys.

## Technical

**`storage.js`**
- `readUnreadableRaw` → **`readUnreadableValues()`**. It returns `{ values: [{key, raw}, …] }`: every present key, in
  loadState's order (current, then legacy), so `values[0]` is the value the load read. `{gone}`, `{error}` (getItem
  threw) and `{unlocked}` are as before. The old function had one caller and is removed, not left dead.
- **`keepUnreadableCopy(raw, sourceKey, now)`**
  - The key names its source: `workout-mvp-unreadable-<ISO>-v8`.
  - **De-dup:** it scans existing keys (`localStorage.length` / `key(i)`). A copy of the **same source** with `===`
    content is returned as `{ key, reused: true }` and nothing is written. A differing value gets its own copy.
    req-157's unsuffixed copies name no source, so they never match, and they're left as they were.
  - **Never overwrites another copy:** a same-millisecond (or clock-set-back) second write gets `<ISO>~2-v9`, `~3`, …
  - A throw in the scan returns `{error}`.
  - A setItem throw returns `{error, quota}`. `quota` is true for `QuotaExceededError` /
    `NS_ERROR_DOM_QUOTA_REACHED` / code 22.

**`import-backup.js` `importWithBackup`**
- It copies every value (one timestamp per Import). Any copy failure aborts with the lock kept and nothing saved.
  Copies already written stay.
- **Download unchanged:** it's still one `.txt` of `values[0]`, the value the load read.
- New **`KEEP_NO_SPACE_MESSAGE`** when a copy fails with a quota error. Every other failure keeps
  `KEEP_FAILED_MESSAGE`.

## Workflow

- **For Emilio (his call):** the storage-full wording, `KEEP_NO_SPACE_MESSAGE`:
  > Couldn't keep a copy of the unreadable data: this browser's storage is full. Nothing was imported, and the data is
  > still stored as it was. To make room, clear the website data of other sites in your browser's settings (not this
  > app's — it holds the data), then try Import again.

  It warns off clearing *this* app's data, because that would delete the value being protected. Export isn't offered,
  since it would only hold the empty state.
- **Choice the spec left open:** the download stays one file (the value the load read). Downloading one file per key
  would trigger the browser's "multiple downloads" prompt. The on-device copies are the safety net (DEC-086), so no
  behaviour a user sees in the download changed. Possible DEC.
- **Bug found and fixed on the way:** the ISO-only key meant a second copy in the same millisecond **overwrote** the
  first, breaking "never delete one". The first test run was flaky (1 of 3 red), which is how it showed up. Fixed with
  the `~n` suffix and pinned by a test. With per-second-apart retries it was unlikely on a device, but it was real.
- **Not verified:** that the `.txt` download fires in the browser. My CDP download capture didn't attach in a
  non-default browser context. That code path is unchanged from req-157, and the unit tests cover the call and its
  order (after every copy, before the lock lifts).
