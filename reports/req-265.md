## Technical

- **The generator:** `libraryHintEntries` and `libraryHintsText` live in `src/library-hints.js`. Each entry keeps `id`, `name`, `displayName` (if present), `aliases` (if not empty), `unilateral: true` (only when true) and `formCues` (non-blank, at most `REST_CUES_MAX`, only when there are any). Absent fields stay absent. `restNotesFor` and the generator share one `restCuesOf`, so the cue filter cannot drift. The file is written one entry per line, so a library rebuild shows a per-exercise diff.
- **The build script:** `scripts/build-library.mjs` writes `src/library/hints.json` from the same `deriveLibrary` output as `exercises.json`.
- **The loaders:** `src/exerciseLibrary.js` has a new `lazyChunk(importer)`, which caches the load and drops the cache on failure. `loadExerciseLibrary` and the new `loadLibraryHints` are both built on it. The reset behaviour is unchanged (`exerciseLibrary.test.js` "next open retries" still passes).
- **The hook:** `useExerciseLibrary` (`src/views/workout/use-library.js`) loads `loadLibraryHints`. It has an injectable `load` argument, used only by tests. Its callers did not change: `item.jsx:336, 885` and `Exercises.jsx:447`. All three read the library only through `library-hints.js` (`isEachSide`, `restNotesFor`, `unilateralPatch`). The picker, search and catalog (`exerciseCatalog.js:23`) still load the full library.
- **Choices the spec left open:**
  1. The generator is in `library-hints.js`, not in `build-library.mjs`. The script has top-level side effects (a fetch, file writes), and the generator needs `REST_CUES_MAX`.
  2. There is no separate resolver: `libraryEntryFor` works unchanged on either list.
  3. `hints.json` contains only entries with the fields that matter. It is not a fixed-shape record.
- **Test edit, called out:** `src/req-217.test.js` now also runs `await loadLibraryHints()` at the top, next to its existing `await loadExerciseLibrary()`. That earlier line had pre-loaded the hook's chunk, so one `settle()` tick was enough for the hook. Without the new line, the render test failed once under full-suite load. No assertion changed.

## Workflow

- **Finding for Planner: a failed lazy chunk is never re-fetched until the page reloads.** Chrome caches a failed dynamic `import()` in the module map, so the same URL rejects again with no network request. This is shown in the probe output above. The `promise = null` reset (criterion 4, kept) makes a second `import()` call, but in the browser that call cannot succeed. In the app, a hints chunk that failed once shows plain reps and no cues until the next reload. A reload recovers, as shown above.

  This predates the branch. main's `exercises.json` loader works the same way, which includes the catalog's "next open retries" from req-139. That test passes in Node only because it injects a fake importer. Fixing it would mean a cache-busting retry URL, which Vite cannot analyse statically. That is out of scope here; it could be a small req if a re-fetch on the next open matters. Criterion 4 as written (renders as without a library, no error, the reset kept, a later mount calls the import again) is met. "Retries" in the sense of a new network fetch is not.
