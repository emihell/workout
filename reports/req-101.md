# req-101 — repair the rotted NOW.md↔status drift check + planted-failure self-test

Branch `req-101`. Tooling only (`scripts/check_handoff.py` + a new manual shell test). No app
code, no persisted data. Ready to look at — not merged.

## Technical

### The bug (reproduced)

`parse_now_md_claims` extracted `{}` from the current NOW.md: its `DONE_LINE_RE`/`QUEUE_LINE_RE`
expect a `done <date>:` / `[ ] req-N … TAG` checkbox format the doc no longer uses, so the whole
NOW.md↔status cross-check ran on an empty claim set and could never fire (L-020).

```
$ python3 -c 'import sys;sys.path.insert(0,"scripts");import check_handoff as c;print(c.parse_now_md_claims(open("handoff/NOW.md").read()))'
{}                                  # before
```

### The fix — `scripts/check_handoff.py`

**1. `parse_now_md_claims` is now section-aware** (`:242`–`:309`). It keeps the two legacy regex
layers (in case those formats return) and adds a line scanner keyed off NOW.md's *stable
structure*, not a checkbox format. A `req-N` under a **forward-looking region** becomes a
`"pending"` claim (NOW.md asserting it has not shipped). Two independent "inside a forward-looking
region" signals:

- a `## Needs decisions …` section header (`NEEDS_DECISION_HEADER_RE`) — holds until the next `##`;
- a bold-label block that *opens* with `**READY…` or `**IN FLIGHT…` (`FORWARD_LABEL_RE`, anchored so
  the bold content must *start* with the label) — holds until a blank line, a new header, or a new
  bold label.

Everything else is left alone: the top `**Shipped: …**` summary, `LIVE`/aftermath prose,
`## Milestone`, `## Where to read`. The anchoring is what keeps `**Nothing in flight.**` (a sentence
that names shipped reqs) from being mistaken for the `**IN FLIGHT:**` label.

**Judgment call (spec left this to me):** section boundaries are done with a **small line-by-line
state machine**, not a header-index scan. It was the simpler thing that passes the planted-failure
test and handles NOW.md's mix of forward-looking and LIVE content *inside the same `## Next`
section* — a whole-section approach can't, because `## Next` legitimately holds both.

**2. `_now_claim_disagrees` extended** (`:312`) with one conservative rule: a `"pending"` claim
disagrees **only** when the doc classifies as `merged`. `unknown` / `not-merged` / `blocked` are all
consistent with "not shipped yet" and stay silent — no false positives.

**3. Moved the now_claim disagreement check to the top of `check_status_lines`'s loop** (`:339`).
It was at the tail, but the `merged` / `blocked` / `unknown` branches each `continue`, so for a
**merged** req the check never ran — which is exactly the drift req-101 targets (a merged req listed
as still-pending). Checking first, for every category, is what makes the merged case reachable.

### The self-test — `scripts/check-handoff.test.sh`

Manual, **not** wired into `./check` (precedent: `plan-guards.test.sh`, `plan-ledger.test.sh`).
Because `check_handoff` reads `handoff/` via `git show`, it builds a throwaway committed git repo,
plants `req-200` as genuinely shipped (BUILT AND MERGED + a real `req-200: …` landing commit that
touches code), and swaps NOW.md between a drifted layout (merged req under `**READY, held:**` and
under `## Needs decisions`) and a correct one (merged req only under `**Shipped:**`). `req-201` is a
pending-not-merged control that must stay silent in every layout. Case 4 monkeypatches the parser
back to the regex-only form to prove the fix is what makes the check fire.

### Item #3 — sibling-parser rot (spot-check findings; fixed none, per "don't scope-creep")

1. **`check_backlog_index` (`:353`) is FULLY ROTTED — same L-020 class, and worse than the bug this
   req fixed.** Its `TIER_DIR` `handoff/work/backlog/` **no longer exists**, and BACKLOG.md has
   dropped the `## Sections` / `**§N.N**` index and the `### N.N` tier headings entirely (current
   BACKLOG uses `## Phase N` sections and `- **\`req-NN\`…**` bullets). So it scans zero headings and
   zero index entries and can never fire. **Not trivial to fix** — the thing it validated
   (`§N.N` cross-reference integrity) no longer exists in the doc model, so repairing it is a
   redesign, not a regex tweak. **Recommend a follow-up req.** (This is arguably higher priority than
   req-101 was, since it's a whole check that's dead.)

2. **`classify_tag` (`:214`) minor rot:** it matches `NEEDS DECISIONS` (plural) but the docs write
   `NEEDS DECISION` (singular), so a parked req like req-24 classifies as `unknown` instead of
   `not-merged`. **Non-failing** (`unknown` findings are verbose-only, "not a failure"), so it does
   not affect this req's drift check (req-24 stays silent either way). Trivial to fix
   (`DECISIONS?`), but it would flip req-24 to `not-merged` and trigger a `find_merge_evidence`
   lookup — a behavioral ripple I left alone to stay conservative. **Noted for a follow-up.**

3. **`check_size_claims` (`:435`) is NOT rotted, just dormant.** The active NOW.md ≤50-line rule
   still fires (NOW.md is currently exactly 50). The per-file "N lines" and "Nth longest file"
   parsers currently match nothing only because the docs were trimmed of such claims — the formats
   they expect are generic prose, not a dead checkbox format, so they'd catch a real claim if one
   returned. No action.

### Known limitation of the fix (surfaced, not a defect)

The section scan collects **every** `req-N` under a forward-looking region. If a forward-looking
bullet ever referenced an already-shipped req as context ("depends on req-50, which shipped"), that
would be a false positive. The current NOW.md has no such case, and the conservative
`_now_claim_disagrees` only fires on `merged`, so it's clean today — but worth a note if NOW.md's
style shifts. If it becomes a problem, the fix is to scope collection to the req that "leads" a
bullet rather than every mention.
