## Technical

- `src/sync/merge.js`: new `dropFinished(out, conflicts, kind)`. When the merged `activeWorkout` is in progress and its id is in the merged `workouts`, it sets `activeWorkout` to `null` and pushes `{ field: 'activeWorkout', id: null, kind, lost: <the dropped workout, verbatim> }`. `mergeStates` now calls it with `finished-elsewhere`. `mergeWithoutBase` calls it with `no-base-finished`, which keeps the same behaviour (the code moved out unchanged). The engine rebase (`engine.js:206`) gets the fix through `mergeStates`.
- `server/ops.mjs` `duplicateWorkoutIds(dbFile)` / `readOnlyDb(dbFile)` (`DatabaseSync … { readOnly: true }`) check each user's latest revision. The command is `./server/ops duplicates [<db file>]` (`ops-cli.mjs`).
- Dependents checked: both merge callers (`server/store.mjs:196` putState, `src/sync/engine.js:206` rebase) and `server/merge.mjs` (a re-export). The guard only fires when the in-progress workout's id is already in the merged history. No app path puts a finished workout's id back into `activeWorkout`: I grepped every `activeWorkout:` writer in `src/`, and `startedWorkoutState` makes a new id. So a legitimate workout is never dropped (criterion 2 and test 4).
- **Review fixes (`dd43de5`):**
  1. `mergeStates` passes `dropFinished` the other side's `activeWorkout` (the side the merged one did not come from). If that one has an id and the id isn't in the merged history, it is kept unchanged instead of `null`, so every value still comes from an input. Any `activeWorkout` conflict that listed it as `lost` is removed, because it wasn't lost. The stale copy is listed as `finished-elsewhere` as before. `mergeWithoutBase` passes no `other`, so it still sets `null` when it drops one.
  2. Ids are matched only when `active.id` is non-null, and history entries that aren't objects are skipped. This applies to both merges.
- **DEC-155 §9 (`95b6c19`): what the app's rebase drops goes to the server.**
  - `src/sync/engine.js`: `rebaseOnto` keeps `mergeStates(...).conflicts`. `addPending` stores them in the sync meta, and the merged state is not changed. The rebase runs twice per reply (on `latest`, then as the store update), so `addPending` keeps each conflict once by deep-equality.
  - Pending conflicts force a push (`changedHere`, and `again` in `accept`). The push sends them as `conflicts` in the PUT body. After a 2xx reply, the ones that were sent are removed; any added since stay.
  - **Push fails** (network, 5xx, 401, 413 or another 4xx): all of them stay pending, and the next push that succeeds sends them, after a reload too.
  - On first login as a different user, the pending conflicts are cleared, because that path replaces the device's data with the account's.
  - **New sync-meta field:** `pendingConflicts: []` in `workout-sync-v1`. Its shape is the merge's `{field, id, kind, lost}`, and it survives a reload. `setMeta` keeps entries another tab added since this tab's last write, the same way it already handles `dirty`.
  - `server/store.mjs` `putState` accepts an optional `body.conflicts` and validates its shape (otherwise 400). Those conflicts are appended to the revision's own `conflicts` through the same INSERT, so there is no second store. A push that carries conflicts makes a revision even when the state equals the server's (this reuses the existing `conflicts.length === 0` short-circuit). A conflict already stored on a revision after the push's `baseRev` is not stored again: this covers a retry after a lost reply. Without a base (`diverged`) there is no such check. The app sends `conflicts` only when it has some, so older apps are unaffected.
  - Test harness: `deviceFetch` gained `holdGet`, which parks GET replies the same way `hold` parks PUT replies. This is one added line, and no existing test line was changed.
  - Which conflicts go up. In `95b6c19` every conflict the rebase listed was sent, including entries whose `lost` is the server's own value.
    - **Planner's decision (DEC-155 §9), `c2b099a`:** send, and force a push for, only conflicts whose `lost` value came from the local side. The server's revision history already holds its own values, and sending them would add a revision per rebase (F-SYNC-2 growth).
    - "Local" is decided by reference against the merge's `mine` input, in `engine.js` `fromLocal`. `mine` is `norm(prev)`, a fresh copy, so a value from it is never the server's object. `mergeStates` and the merged state are unchanged.
    - In the rebase direction (`mine` = local, which wins `resolve` conflicts), the only local-side lost value today is the dropped activeWorkout (`finished-elsewhere`). The filter also accepts any future local-side entry. Test 5 covers a rebase where only the server's value lost: nothing pending, nothing recorded, 4 revisions.
- Nit, left as is: `ops duplicates` on a closed WAL DB creates `-shm`/`-wal` sidecar files. The main file stays byte-identical (as the reviewer reported; I did not re-measure it).
- **Choices the spec left open:**
  1. The check also prints `workout in progress <id> is also in history` for each user. This is the state that comes before the duplicate, and the line is read-only and cheap to print. It is not counted in the total.
  2. (Resolved by DEC-155 §9 in `95b6c19`; kept for the record.) Engine path: when the app's own rebase drops the late-set copy, the `lost` value stays on the device and is thrown away (`rebaseOnto` takes `.state` only). The next push carries `activeWorkout: null`, which merges with no conflict. So in that path the late set is **not** kept in the server's conflict record. It is kept there only when the server's merge drops it (criterion 1). DEC-155 §8 says the set "survives only in the server's conflict record", which holds for the server-merge path but not for this one.
