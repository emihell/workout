# req-171 — Back returns to the screen you came from

Branch `req-171` (off main `63f4554`). Lane: bug. Not merged.

## Technical

**Mechanism.** This reuses req-99's `?from=`, now generalised:

- `route.js` `parseRoute` reads `?from=` on **every** route, not only exercise-edit. It keeps the value only if all of these hold: it is not empty, it decodes, it starts with `/` (and not `//` or `\`), and its path matches a route shape (`matchRoute`, which is the old `parseRoute` body returning `null` where it used to fall through to Today). Otherwise it drops the value, so Back falls back to the fixed parent.
- New helpers in `route.js`:
  - `withFrom(path, from)` builds a link that carries `from`.
  - `childLink(child, here, from)` links to a screen whose fixed parent is `here`. When `here` itself has a `from`, the link carries `here?from=…`, so the chain unwinds one screen at a time.
  - `findInFromChain(from, match)` serves exits that jump past the immediate parent (e.g. recalc → the workout).
- `views/history/return-paths.js` (new, JSX-free, so it can be unit-tested) holds the History Back and exit targets.
- There is no `history.back()`, no timers, no popstate (DEC-084), and no stored data is touched. Nothing under `store.jsx`, `model.js` or storage changed.

**Links that now carry `from`:**
- Today's two history rows (`from=/`).
- History month rows (`from=/history/month/M`).
- The overview's "View in History" (`from=` that preview).
- The exercise-history list's rows (`from=/history/exercise/X`).
- The Library type list's rows (`from=/exercises/type/T`).
- The History detail, one-exercise, set and picker screens pass it down via `childLink`. The exercise detail passes it to Edit.

**Exits honouring it:**
- Detail: Back and Delete.
- Edit: Back, Cancel and Save.
- Add-set picker: Back.
- Add-set form: Back and Cancel.
- Set edit: Back and Cancel. Its Save and Remove carry the chain on to the recalc.
- Recalc: Back, Skip and Apply.
- Exercise detail: Back and Delete.

## Workflow

- **Two bugs outside the spec's table, fixed by the sweep:**
  - A workout opened from a **History month list** Backed to `/history`, not the month. (The spec's table listed the History list as an entry but not this mismatch.)
  - An exercise opened from a **Library type list** Backed to `/exercises`.
- **Left as is, needs Planner's call (rows 33–34):** the active workout overview Backs to Today even when the workout was started from Routines ("Start new workout" → `/routines` → Start). I treated the overview as the workout's hub rather than a child of whatever started it: the Routines picker is a step that Start consumes, and a resumed workout has no meaningful "came from". Threading `from` through the in-workout flow would touch every `go('/workout/…', {replace})` and `ExercisesLink`. If Emilio wants Back → Routines there, that should be its own req.
- **Known limit:** recalc → Routine → an inner routine editor screen → back up. The routine flow's inner screens (`navForBase` paths used as URL prefixes) don't carry `from`, so after going deeper than the routine's own screen, the chain falls back to the plain recalc → plain detail → `/history`. The routine's own screen does return to the recalc with its `from`. It's rare (only reached after editing a set and choosing Routine), and threading it through would mean reworking `navForBase`.
- **A choice the spec left open:** a `from` with a valid route shape but a stale id (e.g. `/history/deleted-id`) is accepted and would render "Not found." on Back. I validate shape, not store contents; only a hand-made or stale URL can produce this.
- **Candidate `DEC-`:** "A screen with more than one way in gets `?from=`, validated in `parseRoute`. Links down use `childLink` so the chain unwinds; exits past the parent use `findInFromChain`." This is the rule future multi-entry screens (req-144) should follow.
- **Candidate `L-`:** `./check --smoke` builds **HEAD's committed tree**. My first green smoke run was main's code, because nothing was committed yet. Commit before trusting the smoke line.
