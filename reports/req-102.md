Branch `req-102`. Tooling only: `scripts/check_handoff.py` + its self-test
`scripts/check-handoff.test.sh`. No app code, no persisted data.

## Technical

Three fixes, each with a self-test assertion.

**Fix 1 — retired the backlog-index check.** Removed `check_backlog_index`, its
call site in `run_checks`, and the constants used *only* by it: `TIER_DIR`,
`SECTION_HEADING_RE`, `UNNUMBERED_HEADING_RE`, `INDEX_ENTRY_RE`. `BACKLOG_PATH`
stayed — it's still used by `LIVING_DOCS` in the size check (grepped before
deleting; `check_handoff.py:467`). Left a short note where the check stood, and
updated the module docstring ("Two checks" now) and the `Finding.check` field
comment which listed the now-dead `"sections"` value. The note deliberately does
**not** spell the retired function name, so the criterion below holds.

**Fix 2 — `classify_tag` singular + plural.** Widened `\bNEEDS DECISIONS\b` to
`\bNEEDS DECISIONS?\b` (`check_handoff.py:225`). Docs write the tag singular, so
a parked req had been classifying `unknown` instead of `not-merged`.

**Fix 3 — NOW-scan claims the bullet's subject req only.** In
`parse_now_md_claims`, the forward-looking-line loop changed from
`REQID_RE.findall(line)` (every mention) to `REQID_RE.search(line)` (the first —
the subject, in practice the backticked token opening the bullet). Section-
boundary logic from req-101 is untouched. The accepted tradeoff (a bullet
introducing two new reqs claims only the first) is noted in a comment.

## Workflow

- No scope added or dropped; the three fixes and their self-tests are exactly
  the spec.
- One judgement call the spec left implicit: the acceptance criterion is
  `grep -c check_backlog_index → 0`, so the retirement note in the source could
  not name the retired function verbatim — I first wrote a note that did (grep
  returned 1) and reworded it to "a backlog-index validator". Flagging in case a
  future reader wants the exact old name findable — it isn't, by criterion.
- Also updated two stale in-file docs that referenced the retired check (module
  docstring's "Three checks" → "Two checks"; the `Finding.check` comment's
  `"sections"` value). Not called out in the spec's step list but implied by
  "retire … and any now-dead" — leaving them would have been the same doc-rot
  the sweep exists to kill.
- Test-harness gotcha worth a possible L-: on this machine's Python 3.9,
  loading `check_handoff` via `importlib.util.module_from_spec` breaks its
  `@dataclass` (the decorator needs the module in `sys.modules`). The existing
  test used `sys.path.insert` + `import check_handoff`; my new heredocs must use
  the same pattern (they now do). Anyone adding inline-python assertions here
  should follow that precedent, not `spec_from_file_location`.
- **Review fix (Planner, 2026-09-18):** my first Fix-1 assertion ran
  `check_handoff --repo $ROOT --ref HEAD` and asserted exit 0. That was
  environment-fragile and, worse, **red on its own branch**: on `req-102`, HEAD
  carries this req's own doc (Status: SPEC — READY = not-merged) *and* its
  implementing commit, so check_handoff's reverse check ("tagged not-yet-merged
  but `<commit>` already merges it") correctly fires → exit 1. My manual receipt
  and the pre-commit test run both passed only because they ran against
  main-state (default ref / still on `main`), not `--ref HEAD` on the branch.
  Replaced the assertion with import + `run_checks` executes without raising
  (environment-independent; that's the actual intent — "retirement didn't break
  the module"). "Runs clean on a clean tree" is already covered by case 3
  (`NOW_CORRECT` → exit 0, empty).
- **L- candidate:** `check_handoff --ref HEAD` on a feature branch flags that
  branch's own not-yet-merged req (its implementing commit is in HEAD's history);
  run it against `main`/`planning` (as `plan save`/`publish` do), and put
  self-test intent in a fixture, never "zero findings on live HEAD". Same
  branch-checkout artifact seen in req-101 review.
