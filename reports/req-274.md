## Technical

- **(a)** `workout-items.js`: new `canAddSet(item)` (`workCountFor(item) < MAX_SETS`). `addWorkingSetToState` skips an item at the cap, so it returns the same state. `item.jsx`'s `ExerciseReview` renders "Add set" only when `canAddSet`. `historyPrescription` slices the working sets to `MAX_SETS` before building `sets`/`targets`/`suggestedWeights`, so all five callers get the first 20.
- **(b)** `workout-items.js`: new `setMatchesItem(set, item)`. `setsForItem` uses it. Keyed rules are unchanged. A set with no key still matches by exerciseId, as before. New: a key-less item (no `id`, no `routineItemId`) also matches a `history-…` set of its own exercise. Nothing is written to storage. Matchers that had their own rule and now use the helper:
  - `model.js` `progressionForItem` `workSets` (was its own `routineItemId || sessionItemId` rule). The legacy `sessionItemId` is first read as `routineItemId` on both set and item. That keeps the req-40 test `model.test.js:272` passing unchanged; I did not edit any existing test.
  - `library-hints.js` `restNotesShowing` (was `last.routineItemId === itemKey(item)`)
  - `views/workout/item.jsx` `WorkoutSetEdit`'s set → item lookup (was `itemKey(candidate) === set.routineItemId`)
  
  Left alone, on purpose:
  - `model.js:116`, migrate's legacy backfill. It already matches by exerciseId and runs inside the migration.
  - `views/history/snapshot-item.js` `snapshotItemFor`. It maps a group key to an item and already falls back to exerciseId.
- **(c)** In `progressionForItem`, `to` is the snapshot item's own `suggestedWeights` when `!isWeightedType(exercise.type)`. `targetsTo` still comes from the recommendation, and `writesRoutine` is unchanged (cardio stays `false`). This means an old snapshot that already holds `[0]` on a bodyweight item (db.json's legacy shape) still writes that `[0]`: it is the item's own data, as the spec's wording says. Only the recommendation's invented `[0]` is gone. That is a choice the spec left open (cardio drops the write entirely). If old `[0]`s should be scrubbed too, that is a separate decision.
- **(d)** `historyAddSetBack(workoutId, itemId, known, from, workouts)` runs `liveFrom` on `from`. If `from` is stale, it takes the existing detail/exercise fallback. Called without `workouts`, it behaves as before. `edit.jsx` passes `store.workouts`.
- No schema change, no migration, no bulk write.
