## Technical

- **Criterion 1, server.** `ClientError` takes an optional `code` (`server/store.mjs`). The `deviceConflicts` 400 throws with `code: BAD_CONFLICTS` (`'bad-conflicts'`, exported). `server/app.mjs` adds `code` to the error body only when one is set, so every other error body stays the same.
- **Criterion 1, app.** `src/sync/engine.js` exports `BAD_CONFLICTS` with the same text; a test asserts the two are equal. In `syncState`, before `settle`, a PUT answered `400` with that code, sent with a non-empty `sentConflicts`, does three things: it removes only the conflicts it sent from `pendingConflicts` (the same filter as the success path, and `setMeta` keeps any another tab added), writes one `console.warn` with the count and the server's message, and sets `again = true`. The `run()` loop then pushes again in the same sync. `dirty` stays true, so the next round pushes. The `error` value is not touched, so the push that succeeds clears it. No loop: every refusal removes at least the conflicts it sent, and an empty list never takes this path.
- **Criterion 2, merge.** `mergeWithoutBase` (`src/sync/merge.js`) now works out `other` the same way `mergeStates` does: `out.activeWorkout === mine.activeWorkout ? theirs.activeWorkout : mine.activeWorkout`. It passes `other` to `dropFinished`. In the probe case, `dropFinished`'s existing rule removes the `no-base-in-progress` conflict that listed wo-new as lost.
- **Criterion 3, ops.** `readOnlyDb` (`server/ops.mjs`) opens `file:<path>?immutable=1` (read-only) when `<db>-wal` does not exist. Otherwise it opens the file as before. `duplicateWorkoutIds` is the only function that calls `readOnlyDb`. The other read-only opens in `ops.mjs` / `ops-cli.mjs` call `DatabaseSync` directly, and the spec scopes this to callers of `readOnlyDb`, so they are unchanged. They may leave the same sidecars; that is a possible follow-up.
- **Choices the spec left to me:**
  - the code value `'bad-conflicts'` as a shared constant
  - the warn text: `sync: the server refused N conflict record(s); dropped them and pushed the state without them. Server: <message>`
  - the URI is built with `pathToFileURL(dbFile).href`, so paths with spaces or `#` are encoded
- **Known gap [inferred].** A writer could open the DB between the `-wal` check and the immutable open. The check would then miss what that writer adds. This is only possible when the server starts during the check, and the check reads only.
- **Verified:**
  - **On the real server:** test 1b sends a badly shaped list to the throwaway server. The real 400 carries the code, the list is dropped and the state reaches the server.
  - **The req-268 read-only test still passes** (a write through the handle is refused, the file stays byte-identical), now through the immutable path.
