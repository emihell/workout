## Technical

- `src/views/routine-nav.js` — `navForBase` takes an optional `from` (the routine screen's own `?from=`). With it, each
  link down carries the chain (`edit`, `pick`, `item(id)` carry the routine-with-from; `create`/`newItem` carry the
  chained picker; `createManual`/`createSearch` carry the chained hub; `change(id)` carries the chained item). It also
  returns a new `up`: the routine screen with its `from`. With no `from`, every string is what it was and `up === base`.
- `src/views/Routine.jsx` — every inner exit that read `nav.base` now reads `nav.up`: Edit Back/Save/Cancel, picker
  Back/Cancel/Add, new-item Save, item Back/Cancel/Save/Remove. `base` stays a plain path prefix. The create screens
  get `nav={paths}`.
- `src/views/Exercises.jsx` — `createPaths(returnBase, nav)`: with a `nav`, the hub/picker/manual/search/afterCreate
  paths come from it, so the create flow keeps the chain. The plain `/routines/:id/exercise/create*` routes in `App.jsx`
  pass no `nav` and are unchanged.
- `src/views/history/return-paths.js` — `liveFrom(from, workouts)` drops a `from` whose route names a workout id not in
  `workouts`. `historyDetailBack`, `historyExerciseBack` and `historySetBack` take `workouts` as a last argument and use it.
  `historyRoutineFrom` finds the routine screen's own `from` from any of its screens: the `from` itself on the routine
  screen, and on an inner screen the `from` of the routine-detail hop in the chain (`findInFromChain`).
  `historyRoutinePaths` builds the route set from that.
- `src/views/history/recalc.jsx` (`HistoryRoutine`), `detail.jsx` and `edit.jsx` pass `store.workouts` in.
- Domino check (shared `navForBase` and `Routine.jsx`): AC3 covers routine, schedule-slot and workout-setup with each
  caller's real arguments, and the whole suite (2267 tests) is green.

**Choices the spec left open:**
1. **How `from` reaches the inner screens:** I added an argument to `navForBase` plus a new `up` field. I did not
   overload `base`, because `base` is also a path prefix (`returnBase`).
2. **The create flow (Add exercise → Create exercise → Add manually/Search → the new item)** also carries the chain,
   through a `nav` prop on `ExerciseNew*`. Scope 1 names "its add/create screens"; the spec gave no mechanism.
3. **Which route names count as "names a workout":** the spec's six (`history-detail`, `-workout-exercise`, `-set`,
   `-edit`, `-recalculate`, `-routine`) plus `history-set-add` and `history-set-new`, which also carry a workout id.
   `history-exercise` is left out on purpose: its id is an exercise id.
4. **The stale check also covers the routine screen's own `from`** (`historyRoutinePaths`). A stale one falls back to the
   bare recalc.
5. **`workouts` is optional:** when it is not passed, the `from` is kept as before. The req-171 tests call the helpers
   with two arguments and still pass unchanged. Every view passes `store.workouts`.
6. **Not changed:** `historyAddSetBack` still returns a `history-workout-exercise` `from` as is. `historyDetailReturn`
   only matches the current workout's own id, so a stale id cannot reach it. The spec named only the three helpers.
