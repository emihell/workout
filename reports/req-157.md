# req-157 — Import from the "unreadable data" state keeps the raw value first, then really saves

Branch `req-157`. The fix is in one commit. **Persisted-data work** (DEC-035 carve-out): it changes when the stored
value may be overwritten. There is no schema change, no migration and no bulk write of its own; the overwrite
happens only when the user confirms an Import. `store.jsx` and `workout-log.js` are not touched. `storage.js` is
(two small exports), so the independent reviewer applies, plus the DEC-046 Export reminder, as Planner planned.

## Technical

**`storage.js`** — two new exports. `loadState`/`saveState` are unchanged.
- `readUnreadableRaw()`: while the DEC-032 lock is set, it reads the raw value **fresh from disk** with
  `loadState`'s own key choice (the current `workout-mvp-v9`, else the first legacy key). It returns null when not
  unreadable, when the value is gone, or when storage throws.
- `releaseUnreadable()`: lifts the lock. The only caller is `importWithBackup`.

**`import-backup.js` `importWithBackup`** — the one path both Import sites (Settings, Today) call.

1. Validate first (unchanged; a bad file throws before anything is asked).
2. If unreadable, read the raw value.
3. Ask. The message in that state is *"Replace all data on this device? The saved data that couldn't be read will
   be downloaded first, exactly as stored."*, and it is unchanged otherwise.
4. On confirm in the unreadable state: `downloadText('workout-unreadable-<date>.txt', raw)` (a `text/plain` Blob of
   the string as it is, not re-serialised), **then** `releaseUnreadable()`, **then** `store.applyBackup` →
   `setState` → `saveState` writes.
5. Cancel returns null: nothing is downloaded, the lock stays, and nothing is written.

**Choices the spec left open:**
1. **The raw file replaces the usual pre-import JSON backup** in the unreadable state, instead of adding to it.
   That backup would only hold the empty in-memory state, which is what the audit flagged, and the spec's
   criterion says "one download". Anything logged in that session was never saved and is replaced by the import,
   as before.
2. **Lock set but the value already gone from disk** (e.g. another tab cleared it): there is nothing to keep, so the
   lock lifts and the usual JSON backup runs.
3. **A corrupt legacy key** (`v8`, no `v9` yet) is the file downloaded. After the import writes `v9`, the next
   load's existing legacy cleanup (`removeLegacyKeysIfCurrentPersisted`) removes that `v8` key, which is by then
   downloaded. This is existing behaviour, but it is the one place this change leads to a removal. **Reviewer:
   please look at it.**
4. "Byte-exact" means the stored JS string is written unchanged into a UTF-8 Blob. `blob.text()` reads back
   `===` the stored string, non-ASCII included (tested). [inferred] A lone UTF-16 surrogate would not survive
   UTF-8 encoding; the app's own writes (`JSON.stringify`) don't produce one.

### Receipts

**Unit** [measured] `node --test src/req-157.test.js` → `# pass 6 # fail 0`. The tests run the real
`loadState`/`saveState`/lock against an in-memory localStorage, with a store stand-in that saves the way
`store.jsx`'s `setState` does.
- **Confirm:** 1 raw download equal to the stored string, made while the lock was still set. No JSON backup. The
  lock is lifted, `v9` holds the import (13 workouts), and `loadState()` then loads it, unlocked.
- **Cancel:** no download, the lock is kept, the stored value is untouched, and `saveState` still returns false.
- **Invalid file** (the analytics export): it rejects "Not a workout database backup.", nothing is asked or
  downloaded, and the lock and the value are unchanged.
- **Corrupt legacy `v8`:** that is the value downloaded, and `v9` gets the import.
- **Readable state:** the usual message and JSON backup, and no raw download.
- **`downloadText`:** the Blob is `text/plain` and its `.text()` `===` the string.

**Browser** [measured]. Isolated origin: `git archive req-157` → `vite preview` on `127.0.0.1:4177`. The app's
