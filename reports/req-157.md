**Persisted-data work** (DEC-035 carve-out): it adds a new localStorage key and changes when the stored value may be
overwritten. There is no schema change, no migration and no bulk write. Writes happen only when the user confirms an
Import. `store.jsx` and `workout-log.js` are not touched. The reviewer re-runs, plus the DEC-046 Export reminder.

## Technical

**`storage.js`** — new exports. `loadState`/`saveState` are unchanged.
- `readUnreadableRaw()` reads the raw value fresh from disk with `loadState`'s key choice (the current `v9`, else
  the first legacy key). It returns one of:
  - `{ raw }`: the value is there;
  - `{ gone }`: getItem answered and there's nothing stored;
  - `{ error }`: getItem **threw**;
  - `{ unlocked }`: the lock isn't set.
- `keepUnreadableCopy(raw)` writes `workout-mvp-unreadable-<ISO time>` with `setItem`, then reads it back.
  Only an exact `===` counts; anything else, or a throw, is `{ error }`.
  - The key is **never read, migrated or deleted by the app**. It exists for recovery by hand, and a comment says
    so.
  - localStorage keeps JS strings as they are, so an unpaired surrogate (a value cut mid-emoji) survives.
- `releaseUnreadable()` lifts the DEC-032 lock. The only caller is `importWithBackup`.

**`import-backup.js` `importWithBackup`** (both Import sites call it). The order:
1. Validate the file (unchanged). A bad file throws before anything else happens.
2. Ask. In the unreadable state the message is *"Replace all data on this device? The saved data that couldn't be
   read is kept as a copy on this device and downloaded first."*
3. **After the confirm**, read the raw value.
   - `error` → throw `KEEP_FAILED_MESSAGE`. Settings and Today already show a thrown error inline. The lock is
     kept and nothing is written.
4. `raw`: keep the copy first. If that fails → throw `KEEP_FAILED_MESSAGE` (*"Couldn't keep a copy of the
   unreadable data on this device, so nothing was imported. It is still stored as it was."*); lock kept, nothing
   saved.
5. Download it as `workout-unreadable-<date>.txt`. This replaces the usual JSON backup, which would only hold the
   empty in-memory state. If the download throws → the error propagates with the lock still set.
6. `gone`: there's nothing to keep, so the usual JSON backup runs.
7. **Only after the download call returns:** release the lock → `store.applyBackup` → saveState writes.

**Downloads:** `downloadJson` and `downloadText` share `downloadBlob`, which revokes the object URL **60 s after**
the click instead of synchronously. That also applies to Export and the normal pre-import backup; revoking straight
after the click could cancel them too.

**Reviewer blocker (7731c59), and how each point is addressed:**
- *release/import ran as soon as `click()` returned.* A click proves nothing reached the user (iOS asks
  "Download?" later; a home-screen app can ignore blob downloads). The on-device copy is now kept and verified
  **before** the download and the release.
- *Legacy v8 deleted on the next load.* v8 is still removed by the existing cleanup, but the copy key survives it
  (tested, and checked in the browser).
- *Synchronous revoke.* Now delayed.
- *A Blob turns an unpaired surrogate into U+FFFD.* [measured] `new Blob(['ab\uD83D']).text()` → `'ab�'`.
  The copy key holds the exact string; the download can't, and the code says so.
- Should-fixes:
  - (a) getItem throwing → abort, lock kept; release only on an answered `null`.
  - (b) release only after the download call returns.
  - (c) the raw value is read after the confirm.

**Choices left open (Planner's call, which the spec marks unconfirmed):**
- The copy key uses the ISO **UTC** time (`toISOString()`); the download name uses the local date. At 00:01
  local, that gave `…-2026-09-24T22:01…Z` and `workout-unreadable-2026-09-25.txt`.
- A failed or mismatched copy write is left where it is, not removed, because "never auto-delete".
- Every Import in the unreadable state writes a new copy. A retry after a failed download adds a second copy of the
  same value.
- The copy takes space. If storage is full, the copy fails and the import aborts with the inline error, which is
  the safe outcome.

### Receipts

**Unit** [measured] `node --test src/req-157.test.js` → `# pass 13 # fail 0`. The tests run the real storage.js
against an in-memory localStorage, with a store stand-in that saves like `store.jsx`. The test value ends in an
unpaired surrogate.
- **Confirm:** one copy key (ISO format) `===` the stored string, surrogate included. The download matches and ran
  *after* the copy existed and *while* the lock was set. No JSON backup. The lock lifts, v9 = the import (13
  workouts), a reload loads it, and the copy is still there.
- **Legacy v8:** kept and downloaded. After the reload's cleanup, v8 is gone and the copy is still present.
- **Failures:**
  - the copy's setItem throws (quota) → `KEEP_FAILED_MESSAGE`, no download;
  - the copy reads back different → the same abort;
  - downloadRaw throws → rejects, and the copy stays;
  - getItem throws after the confirm → `KEEP_FAILED_MESSAGE`, no copy.

  In every case the lock is kept and the stored value is unchanged.
- **Read after the confirm:** a value changed between the ask and the confirm is what gets kept and downloaded.
- **Cancel / invalid file:** nothing read, kept, downloaded or saved, and the lock is kept.
- **Value gone** (getItem answered null): the usual backup runs, then the lock lifts and the import saves.
- **Readable state:** unchanged; no copy key.
- **downloadText:** `text/plain`, content equal, revoked by a timer (≥ 1 s), not straight after the click.

  value safe". Possible L-: *a triggered download is not a backup. Keep a verified copy in the same store before
  lifting any write lock.* DEC-032's rule ("never lose the raw value") now covers Import through the copy key.
- **Needs Emilio's eyes before merge** (DEC-035). What changes on his device, and only in the unreadable state
  after he confirms an Import:
  - one new key, `workout-mvp-unreadable-<time>`, which is never deleted by the app;
  - one `.txt` download;
  - `v9` overwritten with the import;
  - on the next load, the existing cleanup removes a legacy key if one was the source.

  No existing record is rewritten.
- **Scope added:** the delayed revoke also applies to Export and the normal pre-import backup (shared helper).
- **Not changed (copy, Emilio's call):** the unreadable banner still says "Nothing you do now will be saved." That's
  no longer true for Import.
